# How to turn a repeated task into a saved method

A plain memory holds a single fact. A repeated way of working holds something bigger than one fact: a method for a whole kind of task, done well, with the reasons behind each part of it. That still belongs in memory, written as a how-to, not as a separate script the assistant is expected to follow point by point. The difference matters: a script gets triggered and executed literally; a how-to memory gets recalled when relevant and applied with judgment, the same way a person recalls how they usually handle something similar rather than reciting a checklist verbatim. When the same kind of task, correction, or explanation has come up three or more times, that is the signal a method is forming and worth writing down.

## Collect the actual method

Look back at how the task actually went each time it came up: what was asked, what worked, and what got corrected along the way. Recall the memories already connected to it: decisions and rules that already apply here. Write down the steps that were genuinely followed in practice, not the idealized version of how it should have gone.

## Write it as a how-to memory

It takes the same shape as any other memory (see [[reference_how_to_save_a_memory]]): a name, a description written in the words someone would actually use when they need it, along with when to read it, the type set to reference, and the same metadata fields as any memory. The body is the method itself: short steps, a table wherever a table makes it clearer, the mistakes worth avoiding, and the why behind the parts that are not obvious. What decides whether this memory ever gets surfaced again is that description, so it needs to name the actual requests that should bring the method back, and, where it matters, the close cases that should not.

Nothing personal, meaning no specific names, accounts, or numbers belonging to one particular case, goes into the method itself; those belong in their own memories, which the how-to can point to by way of recall rather than repeating inline. A step that has to be exact every single time, such as a calculation, a fixed file format, or a specific command, is still described in words here, with the exact command or format given plainly; judgment about when and how to apply it stays in the memory rather than being hidden in a script elsewhere.

## Test it before trusting it

Write three test requests: two that should clearly bring this method back through recall, and one close but different request that should not. For each, check that the description alone would pick the right answer. Then do the task once using only what the memory says, and fix whatever had to be guessed along the way rather than leaving the gap for next time. Trying it with a weaker or smaller model as well is worth doing when possible: a method that only works when the strongest model is running it is not actually finished.

## After it is written

This is still just a memory, so the same closing steps apply as for any memory: check it is not a near-duplicate of something already saved, link it to what it is actually related to, and rebuild the index from the brain folder so recall can find it. There is no separate install step; being a normal, indexed memory is what makes it available everywhere recall already reaches.
